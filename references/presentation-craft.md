# Presentation Craft

The deck is a presentation, not a document. Optimize for what the audience sees, understands, and remembers.

## 1. Start from the takeaway

Write the one-sentence conclusion of the deck before planning slides. Every page should support it.

A useful test: cover the title and ask "what should the audience do or believe after this?" If the answer is unclear, the deck is still a content dump.

## 2. Narrative arcs

Pick one and map pages to beats.

### SCQA (recommended for business / internal proposals)

| Beat | Slide job |
| --- | --- |
| Situation | Shared context the audience accepts |
| Complication | What changed, what hurts, what is at stake |
| Question | The decision / gap the deck answers |
| Answer | The proposal, split across solution + proof |
| Action | What happens next, owners, dates |

### Problem → Solution → Proof

1. Pain (make it concrete, one scene)
2. Why existing approaches fail
3. Proposal (the new mechanism)
4. How it works (pipeline / workflow / product)
5. Proof (metrics, pilot, before/after)
6. Next step

### Demo flow

1. Current pain
2. Agent / product workflow
3. Product tour (mock or screen)
4. Advantages vs alternatives
5. Results + roadmap
6. Ask

## 3. Slide roles

Not every page should look the same. Assign a role before designing:

| Role | Job | Composition |
| --- | --- | --- |
| Opening | State the thesis | Large type, one line |
| Context | Shared facts | Map / timeline / three facts |
| Tension | Make the pain felt | Pull quote, evidence, numbers |
| Mechanism | Explain how it works | Diagram / pipeline / journey |
| Product | Show the thing | UI mock / screenshot + annotations |
| Proof | Make it credible | Hero metric + supporting metrics |
| Comparison | Justify the choice | Two-column contrast |
| Roadmap | Show momentum | Timeline / phases |
| Close | Ask or next step | One sentence + owner |

A 6-page deck should use at least 4 roles; a 10-page deck at least 6.

## 4. Density budget

At 1280×720:

- Title: ≤ 2 lines, 34–40 px
- Subtitle / lead: 1 line, 14 px
- Body: 11–13 px, line-height 1.6–1.7
- Max ~60 Chinese characters per body block
- One dominant element per page (quote, number, diagram, mock, or list)
- If a page needs 9 px text, split it

Reading deck vs speaker deck:

- **Reading deck** (sent by email): slightly denser, self-contained labels.
- **Speaker deck**: fewer words, bigger type; details go in the script.

Ask which one it is if unclear.

## 5. Rhythm

Plan the deck as a sequence of intensities:

- high-impact opener / quiet context / dense mechanism / visual product / quiet proof / strong close
- Alternate light and dark pages; never two dark pages in a row unless intentional
- Alternate dense and sparse pages
- Avoid three consecutive pages with the same card grid

A simple rhythm check: write one word per page (quote, diagram, mock, numbers, list). If three in a row match, change one.

## 6. Data storytelling

- Lead with the delta, not the raw number: "30 分钟 → 6 分钟", not "6 分钟".
- Show a comparison (before/after, us/them, plan/actual) whenever possible.
- Round for comprehension; keep precise values in a note or source line.
- One hero metric per page; 2–4 supporting metrics maximum.
- Always include source/period when the number is external.
- Placeholder or mock data must say `示意` / `UI Preview`.

## 7. Copy

- Titles state conclusions: "汇报耗时从 2 小时降到 15 分钟" beats "项目汇报".
- Keep the user's vocabulary; do not replace domain terms with generic ones.
- Cut filler: "我们可以看到", "值得注意的是", "为了更好地".
- One idea per paragraph; one paragraph per list item.
- Use parallel structure in lists (all verbs or all nouns).

## 8. Before delivery

- Read the deck at 50% zoom: does the hierarchy still hold?
- Read only the titles: do they form a coherent story?
- Check every page for a single visual focus.
- Check the longest line on every page for clipping.
- Check that the footer, page number, and `data-page` agree.
- Check print: one slide per page, no chrome, no transforms.
- Check that dark pages are not the majority.
